# TEST_PLAN.md — 音乐任务管理平台测试计划

## 1. 测试目标与范围

**目标：** 在有限时间内，优先验证最可能影响**任务归属、交付内容、审核结论**的场景，形成可复现缺陷与剩余风险说明。

| 类型 | 内容 |
|------|------|
| 范围内 | 任务列表（含统计/筛选/分页）、领取与制作、提交审核、审核通过/驳回、并发一致性 |
| 非强制 | 性能压测、完整兼容性、系统级安全专项（仅做与业务相关的针对性探测） |

详细用例见 `音乐任务管理平台_测试用例.xlsx`（含前置条件、步骤、预期、优先级）。用例按「业务场景 + 功能模块」组织；数量不作为评分重点，覆盖与选择理由见下文。

## 2. 业务流程拆解与状态转换

### 2.1 角色

| 角色 | 允许操作 |
|------|----------|
| 制作人 | 领取 PENDING；编辑本人 IN_PROGRESS / REJECTED；提交本人可提交任务 |
| 审核员 | 处理 IN_REVIEW：通过 → APPROVED；驳回 → REJECTED（原因 ≥8 字） |

### 2.2 状态机

```
PENDING（待领取）
  └─ 制作人领取 ──► IN_PROGRESS（制作中）
                      ├─ 保存草稿（状态不变）
                      └─ 提交审核 ──► IN_REVIEW（待审核）
                                        ├─ 通过 ──► APPROVED（已通过，终态）
                                        └─ 驳回 ──► REJECTED（已驳回）
                                                      └─ 修改后再提交 ──► IN_REVIEW
```

### 2.3 关键业务约束（预期来源）

1. 同一 PENDING 只能被一名制作人领取（含并发）。  
2. 已被领取的任务不能再次领取。  
3. 仅负责人可编辑 IN_PROGRESS / REJECTED；保存草稿不改状态。  
4. 提交：歌词去空白 ≥20；音频必须 `https://`；提交后歌词与音频应一并保存并进入 IN_REVIEW。  
5. 仅审核员处理 IN_REVIEW；驳回原因 ≥8；并发审核仅一个决定成功。  
6. 顶部统计卡表示**全部**任务各状态数量，不随分页或筛选改变。

## 3. 最高风险与测试优先级

**执行顺序：先业务场景（打通主链路），再功能模块（挖归属/交付/结论风险）。**  
对齐用例前几条：`mtm_scn_0001`～`mtm_scn_0004`。

### 3.1 第一优先级：业务场景（先测）

| 顺序 | 场景（对应用例） | 为什么先测 | 希望验证的规则 | 足以确认问题的证据 |
|------|------------------|------------|----------------|--------------------|
| 1 | 场景1 主路径：领取→编辑→提交（`mtm_scn_0001`） | 主链路不通则后续模块测试失去基准 | 状态 PENDING→IN_PROGRESS→IN_REVIEW；草稿不改状态；提交后内容应保存 | 各步状态/负责人/列表与详情一致；提交后歌词音频可查 |
| 2 | 场景1 分支：驳回后再提（`mtm_scn_0002`） | 闭环「驳回→修改→再审」 | REJECTED 可编辑；再提交回 IN_REVIEW；驳回原因可查 | 驳回原因可见；再提交后状态正确 |
| 3 | 场景2 审核通过（`mtm_scn_0003`） | 决定终态「已通过」 | 审核员可通过；意见可空；进入 APPROVED | 状态已通过；统计卡待审核−1、已通过+1 |
| 4 | 场景2 审核驳回（`mtm_scn_0004`） | 决定驳回结论与回修入口 | 驳回原因≥8；进入 REJECTED；制作人可再改 | 原因落库；制作人可编辑再提 |

**场景阶段关注点：** 路径能否走通、关键状态是否正确、交付内容是否随提交保留。场景中顺带发现的统计/文案等问题可记缺陷，但**不打断**主路径跑完。

### 3.2 第二优先级：功能模块高风险（场景通过后加深）

在主路径可重复的前提下，再证伪下列高风险约束：

| 优先级 | 场景 | 为什么接着测 | 希望证伪的规则 | 足以确认缺陷的证据 |
|--------|------|--------------|----------------|--------------------|
| P0 | 领取唯一性（多用户并发 + 重复领取） | 归属竞态/可被覆盖 | 仅一次成功 | 双方/多次响应；最终 `assigneeId` 唯一（对应 BUG-002） |
| P0 | 并发审核（通过+驳回） | 结论必须唯一 | 并发仅一个决定成功 | 一成一败；最终态唯一 |
| P0 | 直接提交 vs 先存草稿再提交 | 交付是否丢失 | 提交应保存当前内容 | 不存草稿直接提交后详情仍有内容 |
| P0 | 预置数据歌词≥20 | 脏数据进审 | 预置亦须≥20 | 重置后巡检字符数 |
| P0 | 统计卡全量 | 列表可信度 | 统计=全量且不随页变 | 卡之和 vs「N 条记录」 |
| P1 | 通过意见、待审核提示文案 | 追溯与误导 | 意见可保存；提示原因正确 | 请求体字段；文案与负责人对照 |
| P2 | 返回列表是否记住筛选 | 体验 | （需求未强制） | 返回前后页码/筛选对比 |

**不优先：** 纯 UI 美观、多浏览器矩阵、全量性能。

## 4. 测试设计方法

| 方法 | 用在何处 |
|------|----------|
| 状态迁移 | 合法路径（领取→制作→提交→通过/驳回再提）；非法跳转抽测 |
| 角色矩阵 | 制作人/审核员 × 领取、编辑、提交、通过、驳回 |
| 边界值 | 歌词 0/19/20/21；驳回原因 0/7/8/9；音频 http vs https |
| 场景法 | 制作人主路径；审核通过/驳回 |
| 并发 | JMeter：两用户同时领取；同时通过+驳回（同步定时器） |
| 对照法 | 「直接提交」vs「先存草稿再提交」；预置数据 vs 用户自行提交校验 |

用例选择理由：先跑通业务场景四条主/分支路径，再按模块加深并发、边界与统计；单条用例不堆砌无关点，缺陷单独建单。

## 5. 观察到新信息后的方向调整

| 阶段观察 | 原假设 | 调整 |
|----------|--------|------|
| 列表 9 条、统计卡之和 5，且等于当前页 | 统计可能只是展示问题 | **升为 P0**：按当前页聚合，违反「全量统计」 |
| JMeter 并发领取双成功且负责人不同 | 后端可能有锁 | **坐实归属缺陷**，并补「已领取再领」 |
| 并发审核双绿 | 审核可能串行安全 | **坐实结论缺陷** |
| 预置「未读消息」19 字，但自己改再提交有限制 | 提交校验全失效 | **改为种子数据问题**，与「用户提交校验」区分 |
| 直接提交后状态变了、内容空；先存草稿再提交正常 | 提交未落库 | **补对照用例**，定位为提交未保存当前编辑区 |
| 通过意见未进请求体 | 仅展示问题 | 确认为**前端未提交字段** |
| 返回丢失筛选 | 功能缺陷 | **降为 P2 体验**，不占 P0 时间 |
| 重置抓包偶发看不到接口 | 疑似契约问题 | **证据不足不报**，避免误报 |

## 6. 时间分配、未执行项与剩余风险

| 阶段 | 大致占比 | 内容 |
|------|----------|------|
| 业务场景（先） | ~25% | scn_0001～0004：领取制作提交、驳回再提、审核通过/驳回 |
| 功能模块 P0 | ~35% | 并发领取/再领、并发审核、提交落库、预置字数、统计卡 |
| 功能模块 P1/P2 | ~20% | 意见保存、提示文案、返回筛选记忆、列表筛选分页等 |
| 整理与证据 | ~20% | 用例、缺陷单、截图与响应 |

**未执行或未作为缺陷提交：**

| 项 | 原因 | 是否接受 |
|----|------|----------|
| 系统性能压测 | 非强制；已做针对性并发 | 接受 |
| 多浏览器/移动端 | 非范围重点 | 接受 |
| XSS/CSRF 专项 | 时间让给归属与结论 | 接受（搜索注入仅点到为止） |
| 重置是否调用 `POST /api/test/reset` | 界面与接口均可重置，抓包结论不稳 | 接受，不报缺陷 |
| 自动化代码（可选） | 可后续补充；JMeter 脚本已作并发复现手段 | 接受 |

**接受剩余风险的理由：** 先保证业务场景可重复，再投入错领/丢稿/错审类模块风险；未覆盖项不否定已证实缺陷。

**若再增加约 2 小时：** 固化 API/UI 自动化（重置隔离 + 多重断言）；补后端是否校验提交字数的改包对照；终态 APPROVED 内容保护抽测。
